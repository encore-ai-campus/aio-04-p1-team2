# 문의 처리 이력·메일 알림 Supabase 반영 및 검증 보고서

기준일: 2026-11-12 (한국시간)  
대상: `C:\svn\sea_info`, PostgreSQL `sea_info` 스키마

## 결과

누락 테이블 3개를 생성했고 API 서버가 정상 기동했다. 실제 Jira 시험 이슈의 접수·처리 시작·완료가 Supabase 문의 상태와 처리 이력에 반영되는 것을 확인했다. 메일 예약과 전송 결과 저장은 실제 PostgreSQL에서 검증했으나 **SMTP 설정이 없어 실제 메일 발송·수신은 미실행**이다. 실제 SMTP 수신을 포함한 전체 운영 검증 완료를 의미하지 않는다.

- 생성 도구: `tools/migrate_inquiry_workflow.py --apply`를 모듈 방식으로 실행했다.
- 기존 19개 테이블의 구조·데이터를 변경하는 SQL은 수행하지 않았다. 3개 테이블 생성과 기존 문의의 기준 상태 등록을 하나의 트랜잭션으로 처리했다.
- 생성 직전·직후 기존 19개 테이블의 행 수와 전체 행 해시가 모두 동일했다.
- 새 테이블에는 기본키·외래키를 생성했다. 이력 `(inquiry_id, version)`과 알림 `(event_id, kind)`에 고유 제약이 있다.
- 세 테이블의 RLS를 활성화했고 `PUBLIC`, `anon`, `authenticated`에 대한 테이블 권한은 부여하지 않았다. 서버 DB 연결로 접근한다.
- 기존 문의에 과거 처리 이력이나 메일을 소급 생성하지 않았다. 기존 문의의 알림 예약은 검증 후에도 0건이다.
- 실제 시험으로 생성한 앱 사용자·문의·이력·알림·관리자 로그와 임시 Redis 세션은 정확한 시험 ID를 기준으로 정리했다. 기존 사용자·문의·관리자 로그의 해시도 시험 전후 일치했다.

전체 검증 종료 시 댓글 수가 39건에서 41건으로 늘고 게시글 해시가 바뀐 것이 관찰되었다. 사용자가 **다른 곳에서 커뮤니티 작업 중임을 확인**했다. 따라서 생성 직후 데이터 불변 검사와 전체 검증 기간 중 동시 사용에 따른 변경을 구분했다. 댓글·게시글 데이터는 되돌리거나 삭제하지 않았다. 전체 검증 기간의 기존 19개 테이블 해시가 모두 동일하다고 주장하지 않는다.

최종 테이블 수는 22개이며 소스 정의 대비 누락 테이블은 없다.

### 실제 Jira 증거

- 시험 접수번호: `R-1112-5WVN` — 시험 종료 후 앱 DB에서 정리했다.
- 실제 Jira 시험 이슈: `KAN-11` — 완료 상태로 보존했다.
- 순서: 접수 → Jira 처리 중 → 공개 답변 저장 → Jira 완료.
- 서버의 실제 폴링 작업자를 사용했다. 대기 시간을 줄이기 위해 **시험 문의 한 건의 다음 폴링 시각만 앞당겼다**. 기본 60초 주기의 벽시계 성능 시험은 아니다.
- 메일은 접수 예약이 설정 확인 필요 상태로 대기하고, 후속 처리 시작·완료 예약은 앞선 알림을 기다렸다. 실제 발송 성공으로 표시하지 않았다.
- 이후 모의 전송 함수를 통해 실제 PostgreSQL의 예약 점유·순차 처리·결과 저장을 검증했다. 이때의 sent는 모의 전송 결과이며 실제 SMTP 수신 증거가 아니다. 관련 시험 기록은 정리했다.

### 자동 테스트

1. 전체 회귀: `python -B -m unittest discover -s tools -p "test_*.py"`에 해당하는 discovery 실행 결과 **114건, 실패 0, 오류 0, 건너뜀 0**.
2. 최종 보완 후 문의 워크플로·SMTP·화면 관련 재검증: **38건, 실패 0, 오류 0, 건너뜀 0**. 시험 문의 범위로만 작업자를 실행하는 격리 검증 1건을 추가했다. 두 실행의 테스트 수에는 중복이 있으므로 합산하지 않는다.
3. 실제 API·DB·Jira 통합 검증: **16개 확인 항목 통과**.

주요 테스트 파일은 `tools/test_inquiry_notifications.py`, `tools/test_notification_mail.py`, `tools/test_inquiry_history_ui.py`이다. 통합 검증 도구는 `tools/verify_inquiry_workflow_live.py`이다.

## 검증 중 보완한 코드

- 완료 메일 발송 대기 중 공개 답변을 수정하면 기존 예약의 내용을 갱신한다. 수정할 때마다 완료 예약을 추가하지 않는다.
- 메일 전송 응답을 받은 후 연결 정리 과정에서 오류가 발생해도 성공 결과를 오류로 덮어쓰지 않는다.
- 실 DB 검증용 작업자 호출은 시험 문의 ID로 범위를 한정할 수 있도록 했다. 일반 서버 작업자의 처리 범위는 그대로다.
- `.env.example`의 DB 접속값을 예시 자리표시자로 바꾸고 문의 작업자 설정 예시를 추가했다. 실제 `.env`의 접속 정보는 변경하지 않았다.

## 실행 및 운영 기준

API는 최종 코드를 반영하여 `127.0.0.1:8000`에서 실행한다. `/health`에서 PostgreSQL `sea_info`, Redis 정상 연결이 확인된다. 이번 작업에서 Streamlit 브라우저 서버를 별도로 실행하지는 않았다. 관리자·공개 이력 화면은 AppTest로 검증했다.

작업자는 기본 활성화되며 `INQUIRY_WORKER_ENABLED=true`, `INQUIRY_POLL_SECONDS=60`으로 설정할 수 있다. Jira에 연결된 문의의 상태는 Jira에서 변경하고 공개 답변은 앱 관리자 화면에서 작성한다. 완료 상태에 공개 답변이 없으면 완료 메일은 답변 대기로 남는다.

SMTP 발송 결과가 불명확하면 자동 재전송하지 않는다. 발신함 확인 후 미발송임이 확인된 경우에만 관리자 화면에서 다시 예약한다. 전송 시스템 특성상 절대적인 1회 발송을 보장하지 않는다. 이미 발송된 unknown 기록을 발송 완료로 확인·정리하는 별도 관리자 기능은 후속 보완 대상이다.

Supabase Authentication의 SMTP·메일 템플릿은 가입·비밀번호 재설정용이다. 앱의 문의 메일 SMTP 설정과는 별개다. 공개 HTTPS 주소가 없을 때는 고객 메일에 localhost 링크를 넣지 않고 서비스 내 조회 방법을 안내한다.

## 증거 파일

민감한 접속 정보와 문의 본문은 보고서에 포함하지 않았다. 다음 로컬 증거 파일은 SVN 제외 대상 `data/backups/inquiry_workflow_20261112/`에 보관한다.

- `migration.json`: 생성 전후 행 수·해시, 기준 상태 수, RLS.
- `live.json`: 실제 통합 시험 16개 확인 결과, 시험 접수번호·Jira 키, 실제 SMTP 미실행 표시.
- `tests.json`: 전체 회귀 결과.
- `targeted_tests.json`: 최종 관련 테스트 결과.
- `final_health.json`: 최종 API의 DB·Redis 연결 및 필수 문의·알림 라우터 등록 확인.
- `final_db.json`: 최종 테이블·제약·권한과 전체 검증 기간의 해시 비교 결과. 동시 커뮤니티 작업 때문에 전체 해시 일치 항목은 false이며 위 설명과 함께 해석해야 한다.

SVN 서버로의 커밋은 수행하지 않았다.
